# Obsidian + Claude Code 个人知识库实践指南

> 本指南参考了知乎《超详细版：Obsidian + Claude Code 搭建个人知识库实践指南》一文的整体思路，并结合 Claude Code 的真实产品能力做了核对和修正（原文中部分命令是作者自造的伪代码，实际 CLI 并不支持，下文已标注并给出可用的替代方案），供你直接上手实践。

## 一、为什么是这套组合

- **Obsidian**：本质是一个基于本地 Markdown 文件的知识管理工具，核心优势是双向链接和关系图谱——笔记之间靠链接形成一张可生长的语义网络，而不是简单的文件夹堆叠。数据本地存储，适合处理敏感信息，也方便用 Git／云盘做版本管理和备份。
- **Claude Code**：一个运行在终端里的 AI 编程与自动化代理，能读写本地文件系统、执行 shell 命令、理解自然语言指令。因为 Obsidian 知识库就是一堆本地 Markdown 文件，Claude Code 天然可以把整个 Vault 当作一个工作目录来处理。

两者的分工可以理解为：Obsidian 负责"存储与呈现"，Claude Code 负责"整理与执行"。你负责输入原始信息和把关质量，AI 负责归档、打标签、建链接、生成周期性报告和成稿草稿。

## 二、环境搭建

### 1. 安装 Obsidian

1. 从官网下载对应系统的安装包，创建一个新的知识库（Vault），建议存放在非系统盘。
2. 在「设置 → 核心插件」中开启：反向链接、关系图谱、标签面板。
3. 在社区插件市场（需先关闭安全模式）中按需安装：
   - **Dataview**：类 SQL 语法动态生成笔记列表、任务表格
   - **Templater**：支持脚本的高级模板工具
   - **Tasks**：在任意笔记里用 `[ ]` 管理待办，并集中查看
   - **Excalidraw**：手绘风格白板，可嵌入笔记

### 2. 安装 Claude Code（这里对原文做了修正）

原文写的安装命令 `pip install anthropic-cli` 并不是 Claude Code 的真实安装方式。Claude Code 是 Node.js 生态下的 CLI 工具，正确做法是：

```bash
# 需要 Node.js 22+（不同版本要求可能变化，建议装最新 LTS）
npm install -g @anthropic-ai/claude-code

# 验证安装
claude --version
claude doctor   # 检查安装类型、鉴权状态、配置是否正常
```

首次在终端里进入你的知识库目录并运行 `claude` 时，会引导你完成登录授权（可以用 Claude.ai 账号浏览器登录，也可以用 API Key 做无人值守场景的鉴权）。授权时注意 Claude Code 请求的文件访问权限范围，尽量把工作目录限定在知识库文件夹内，避免不必要的全盘权限。

## 三、构建目录结构

沿用原文"文件夹管领域，标签管属性"的原则，是一个经受过验证的思路：一级文件夹划分大领域，标签描述横向属性（状态、优先级、类型），避免用深层文件夹去表达细粒度分类。一个可参考的结构：

```
知识库/
├── 00_Inbox/          # 收集箱：所有未处理的临时信息
├── 01_Daily/          # 每日笔记、复盘、临时待办
├── 02_Reading/        # 读书笔记、网页摘录
├── 03_Knowledge/      # 按领域分类的结构化知识（原子化笔记）
│   ├── 大模型/
│   └── 编程/
├── 04_Projects/       # 项目资料
├── 05_Templates/       # 笔记模板
├── 06_Assets/          # 图片、附件
└── CLAUDE.md           # AI 管理员的角色定义与规则
```

你可以直接把这段结构描述贴给 Claude Code，让它在知识库根目录下用 `mkdir -p` 一次性建好。

要点提示：

- `00_Inbox` 是缓冲区，任何来不及分类的想法先丢进去，定期让 AI 处理。
- `03_Knowledge` 是知识的主战场，所有信息处理完之后都以"原子化笔记"（一篇笔记只讲一个概念）的形式归档在这里。
- 文件夹嵌套建议不超过两层，更细的分类交给标签和 MOC（主题地图）去做，而不是继续拆文件夹。

## 四、CLAUDE.md：定义 AI 知识管理员的"工作合同"

`CLAUDE.md` 放在知识库根目录，是 Claude Code 每次启动时会自动加载的上下文文件。写清楚这份文件，等于把管理规则固化下来，避免每次都要重新解释一遍。建议至少包含以下几部分：

1. **角色定位**：一两句话说明这是你的专属知识库管理员，目标是什么。
2. **核心原则**：文件夹管领域、标签管属性、命名规范（比如短横线命名、日期用 `YYYY-MM-DD`）。
3. **目录结构说明**：一张表，列出每个文件夹的用途和入库规则。
4. **标签体系**：状态标签（`#status/待处理`）、优先级标签（`#priority/高`）、类型标签（`#type/教程`）等，并规定层级写法 `#一级标签/二级标签`。
5. **核心职责清单**，例如：
   - 每日消化 Inbox：提炼观点 → 改写成原子化笔记 → 分类归档 → 打标签 → 建立至少 3 个双向链接
   - 维护 MOC：当某主题笔记数达到阈值（比如 5 篇）时自动创建/更新主题地图
   - 强制执行格式规范：统一套用模板、链接用 `[[笔记标题]]`
   - 每周输出知识网络体检报告：孤立笔记、核心枢纽笔记、标签使用情况、知识缺口
   - 支持知识输出：协助起草大纲、生成报告初稿、提炼 PPT 要点
6. **权限边界**：明确哪些目录 AI 可以读写（比如 `00_Inbox`、`03_Knowledge`），哪些只读（比如 `04_Projects`）。这一条很重要，能防止 AI 误改你手动维护的内容。
7. **内容原则**：忠于原文、注明外部信息来源。

这份文件不是一次写完就不动了，当你发现 AI 反复在某件事上出错，第一反应应该是回去修改 `CLAUDE.md`，而不是每次临时纠正它。

## 五、把重复工作变成可复用命令（原文的关键错误在这里）

原文里出现的 `claude run process_inbox`、`claude ask "..."`、`claude generate "..." --format article` 这类命令，**并不是 Claude Code 的真实语法**，Claude Code CLI 没有内置的 `run`/`ask`/`generate` 子命令。实际上有两种方式可以达到同样的效果：

### 方式一：自定义 Slash Command（交互式会话中使用，推荐日常用）

在知识库根目录下创建 `.claude/commands/` 文件夹，每个 Markdown 文件对应一个可复用的提示词模板，文件名就是命令名：

```bash
mkdir -p .claude/commands
```

例如 `.claude/commands/process-inbox.md` 内容可以是：

```markdown
---
description: 处理 00_Inbox 中的所有笔记，原子化并归档
allowed-tools: Read, Write, Edit, Glob
---
读取 00_Inbox/ 目录下所有笔记，按照 CLAUDE.md 中"职责一"的规则：
1. 提炼核心观点，重写为原子化笔记
2. 移动到 03_Knowledge/ 对应子目录
3. 添加 2-3 个精准标签
4. 建立至少 3 个双向链接
处理完成后列出本次归档的文件清单。
```

之后在 `claude` 交互会话里输入 `/process-inbox` 即可触发。同理可以建 `/update-moc`、`/weekly-review`、`/draft-article` 等命令。（较新版本的 Claude Code 把自定义命令并入了 Skills 体系，写成 `.claude/skills/<name>/SKILL.md` 效果一样，还能支持 AI 自主判断何时调用，两种写法目前都兼容。）

### 方式二：无人值守模式（Headless / `-p` 参数，适合定时任务）

如果想让整理动作在后台自动跑（比如每天定时清理 Inbox），可以用 `-p`（`--print`）参数做非交互式调用，再配合系统的定时任务（cron / 计划任务）：

```bash
# 一次性执行一个任务，输出结果后退出
claude -p "读取 00_Inbox 下的所有笔记，按 CLAUDE.md 的职责一处理并归档" \
  --allowedTools Read,Write,Edit,Glob
```

写入 crontab 示例（每天 23:00 自动整理 Inbox）：

```
0 23 * * * cd /path/to/知识库 && claude -p "执行 Inbox 整理" --allowedTools Read,Write,Edit,Glob >> ~/inbox-log.txt 2>&1
```

注意：headless 模式下不会有交互确认，务必先在交互模式里把对应的 Slash Command 调试稳定，再放到定时任务里；同时用 `--allowedTools` 限定它能用的工具范围，减少误操作风险。

## 六、日常工作流

一套跑起来之后大致是这样的循环：

1. **随手收集**：读到的、想到的、开会记下的，不做任何分类判断，直接丢进 `00_Inbox`（电脑上直接粘贴，手机上用 Obsidian App 或语音转文字）。
2. **AI 编译**：定期（比如每天）触发 `/process-inbox`，AI 把碎片信息重写成原子化笔记，分类、打标签、建链接。
3. **知识结构化**：当某个主题的笔记积累到一定数量，触发 `/update-moc`，AI 生成或更新对应的主题地图（MOC），作为该领域的导航入口。
4. **检索与提问**：交互会话里直接问 Claude Code 关于知识库内容的问题，它可以搜索、读取相关笔记后给出有链接依据的回答。
5. **知识输出**：需要写文章、做汇报时，触发类似 `/draft-article "主题"` 的命令，让 AI 遍历相关笔记，产出一份初稿，你在此基础上润色定稿。
6. **周期体检**：每周跑一次 `/weekly-review`，看孤立笔记、核心枢纽笔记、标签冗余情况，针对性补充和清理。

## 七、长期维护建议

- **人机分工要守住**：AI 负责格式化、建链接、统计分析、初稿合成；你负责输入高质量信息、把控分类边界、审核每一次产出的准确性。AI 也会犯错、会做出看似合理实则牵强的关联，不要盲信。
- **标签体系要克制**：一级标签控制在 10 个以内（如 `#工作`、`#学习`、`#生活`），二级标签细化（如 `#学习/AI`），定期借助 AI 的周报清理冗余、僵尸标签。
- **插件宜精不宜多**：核心配置 + Dataview/Templater/Tasks 之类少数插件，够用即可，插件太多容易拖慢启动速度、引发冲突。
- **备份是本地方案的责任**：Markdown 本地文件没有厂商锁定的风险，但也需要你自己用 Git 仓库或云盘同步工具（Dropbox / OneDrive / 坚果云等）定期备份整个 Vault。
- **定期做体系级复盘**：每季度让 AI 从更高维度审视一次知识结构——哪些领域在扩张、哪些在停滞、目录是否需要调整、`CLAUDE.md` 是否需要更新。

## 八、常见坑

1. 链接是 AI 建的，但链接背后"为什么相关"要靠你自己理解和补充，否则知识网络只是好看，没有真正内化。
2. 文件夹层级别超过两层，复杂分类交给标签和 MOC。
3. 给 Claude Code 的权限要限定在知识库目录内，不要图省事给全盘读写权限，尤其是 headless/定时任务场景。
4. `CLAUDE.md` 要当成活文档持续维护，而不是一次性写完就不管。
5. 不要迷信网上流传的"魔法命令"——遇到看起来像 CLI 子命令但你在官方文档里找不到的写法（比如 `claude run xxx`），大概率是自定义 Slash Command 或者作者简化后的示意，实操前最好用 `claude --help` 或官方文档核实一下真实语法。
